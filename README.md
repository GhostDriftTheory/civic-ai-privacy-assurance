# 自治体AI・プライバシーアシュアランス｜PoC第2弾

> **開発中・正式発表前（暫定公開）**：本リポジトリは公開用の技術PoCです。正式な共同事業・実自治体での実証開始を示すものではありません。HTML等の「クラウドシエン」との協業・共同PoC・役割・社名表示は、協議を前提とした暫定表現です。実施内容と対外発表の表現は、関係者の最終確認を経て確定します。

**必要な情報は使う。条件不足・不整合がある処理は止める。**

架空の住民相談情報を必要な項目に絞り、利用目的・権限・送信先・変換対応・累積開示を検査します。送信条件を通過した場合に限り、PoC内の模擬送信先を呼び出します。返ってきた出力は別のゲートで確認し、条件を満たす下書きだけを職員確認用として採用します。

氏名・詳細住所を渡さずに案内文案を作る場面と、根拠不足、氏名残存、累積上限、出力への再混入、送信結果不明で止める場面を、同じ仕組みで実行できます。

## 最初に見る

**画面で試す：** `civic_privacy_poc_demo.html` をブラウザで開きます。サーバー・APIキー・ログインは不要です。「必要項目だけで使う」→「許可された模擬処理を実行」の順に操作してください。続いて「累積開示」タブで、要求を順に実行します。

**Pythonで実ファイルまで確かめる：** このフォルダで次を実行します。

```console
python poc.py
```

表示された `output/run-識別子/report.html` をブラウザで開いてください。Python 3.10以降の文法を使用しています。追加Pythonパッケージは不要です。環境に応じて `python3` または `py` を使用してください。

**本物の外部送信はありません。** HTML版の送信先役はブラウザ内のメモリ、Python版の送信先役は実行フォルダ内の `outbox/` です。AI役は固定テンプレートです。実住民情報・外部AI・行政システムには接続していません。

## 実用性を見せる7つの場面

| 実演 | 起きること |
|---|---|
| 必要項目だけで使う | 相談分野・年代・世帯区分だけで、AI役の案内文案を得る。氏名・住民識別子・詳細住所・健康メモは送信しない |
| 根拠を補って進める | 利用根拠の参照がない要求をHOLD。デモ上の確認記録を補った新しい要求で再判定する |
| 氏名を外して進める | 氏名が残る要求をREJECT。必要項目に絞った別の要求なら先へ進む |
| 送信先で止める | 同じ情報でも、許可外の送信先には渡さない |
| 出力の再混入を止める | 送信がPASSでも、模擬応答文に氏名を故意に混入させると出力採用はREJECT |
| 結果不明を保持する | 模擬送信後に確認応答が得られない場合、消費を保持し、後続要求をHOLDにする |
| 累積開示を追う | 年代→世帯区分で累積2点。単独なら2点の地域区分を追加すると累積4点になり、上限3点を超えるため止める |

累積開示の最後では、既に渡した固定の年代情報を再利用する要求は通過します。**何でも止めるのではなく、条件を満たす利用の余地を残す**ことを確認できます。

「結果不明」は、デモ上は送信先役が受信したものの、送信側が結果を確定できない状況として実装しています。届いていないと勝手に扱って消費を戻しません。実運用の結果照会・認証・復旧手順は含めていません。

## 送信8条件・出力4条件

### 送信側

P01：登録された合成資料と台帳の対象範囲。P02：利用目的・用途・人間の確認。P03：利用根拠の参照と操作権限。P04：送信先と取扱条件。P05：最終送信内容の項目範囲。P06：元データ・固定変換・最終内容の対応。P07：累積点数の上限。P08：未確定状態・要求IDの重複。

`REJECT > HOLD > PASS` の優先順で8条件を集約します。すべてPASSのときだけ模擬送信先を呼び出します。HOLD・REJECTでも判定記録は残しますが、受信先の呼出し回数は増えません。

利用根拠・送信先の確認記録は**固定のデモ記録**です。これらの値が合うことは、実際の同意・法的根拠・権限・契約・処理地域が確認されたという意味ではありません。個人情報の利用が常に本人同意だけで決まる、と仮定する設計でもありません。

### 出力側

O01：出力と実要求の参照対応。O02：出力の項目・値の範囲。O03：定型文と内容の一致。O04：職員確認用への用途限定。

送信していない、または結果を確定できない場合、出力採用はHOLDです。送信がPASSでも、出力採用がHOLD・REJECTなら `drafts/` は生成しません。**出力の不採用を理由に、送信済みの開示点数は返却しません。**

本PoCの出力採用PASSは、公開デモのプライバシー条件を満たす職員確認用の下書きという意味です。回答の正しさ、実制度への適合、行政上の決定を保証するものではありません。

## 「累積開示」の具体的な範囲

同一の固定対象・固定資料・共有範囲について、模擬送信した項目の集合を逐次保持します。相談分野は0点、年代と世帯区分は各1点、広域地域と所得区分は各2点、上限は3点です。新規項目の点数だけを加えます。

この点数は、**公開実演のための合成制約**です。差分プライバシーのε、再識別確率、現実の危険度、匿名加工情報等の法的判断を表しません。固定された値を持つ項目の繰り返しを新規開示ゼロとするのも、この小さいモデルの仕様です。変化する値、外部情報との照合、受領者間の共謀・転送、複数システム横断の累積状態は対象外です。

ケース切替や「やり直す」は**独立した合成実験の初期化**です。実運用の台帳をリセットできるという意味ではありません。単一プロセスでの逐次処理であり、同時実行・複数端末間の競合制御は実装していません。

通常実行は46ケースと7シナリオの13ステップ、計59記録です。各ケースは独立した初期状態から、各シナリオは一つの台帳を引き継いで実行します。実行ごとに別フォルダを生成します。

Pythonの `outbox/` には、判定に使った送信内容を同じ正規化JSONバイト列で書き出します。確認用画面の表示だけではありません。保存後は記録を読み直し、受信ファイル・採用文案の内容と、出力すべきファイルの数も照合します。

保存記録には要求と許可・不許可の候補内容が含まれます。**このファイル形式をそのまま実住民情報のログへ流用しないでください。** 本版は同梱の合成資料だけを受理する参照実装です。

## 再検証する

```console
# 全ケースを実行
python poc.py

# 累積開示だけを実演
python poc.py demo cumulative

# 結果不明の保持と後続停止
python poc.py demo unknown

# 保存した全実行フォルダを、実ファイルと連続記録まで確認
python poc.py verify output

# HTML版で保存した単独の記録もPythonで確認
python poc.py verify "P2-記録ID.json"

# Pythonの自己テスト
python poc.py test
```

HTMLの「検証と公開範囲」から、Pythonで保存した `records/*.json` を読み込むこともできます。HTMLの「模擬受信JSON」は送信内容そのものです。再検証用のファイルには「検証記録JSON」を選んでください。

再検証は、記録のハッシュ、固定の仕様、元の要求からの再計算、状態遷移の一致を確認します。HOLD・REJECTでも正しく再現できれば再検証成立です。PASSへの格上げはしません。

ハッシュは電子署名ではありません。単独記録の開始台帳は入力されたスナップショットです。`verify output` ではグループ内の状態を順につなぎますが、索引・開始台帳・プログラム自体の正当性を認証するものではありません。記録全体を整合的に作り直せる相手に対する、真正性・完全性の保証はありません。

## Leanの形式モデルと実装の接続

モデルには、55の定理宣言と証明コードを収録しています。主な命題は以下です。

- 送信PASSなら、8条件のすべてが通過する。根拠・履歴が未確認の状態ではPASSにならない。
- 禁止項目や重複要求は拒否され、累積上限超過は送信できない。
- 許可された送信後の点数は上限以内で、点数は減少しない。結果不明では消費を保持して未確定状態にする。
- 出力採用には、許可された送信、応答の確認、要求との対応、許可項目、定型文、職員確認用の用途が必要。
- 記録の再検証は、送信判定・出力採用・消費量を保持する。モデルから実ネットワーク送信や行政上の自動決定は許可されない。

`python poc.py ci` は、Pythonの入力・資料・台帳から原子的な観測を抽出し、Leanで8条件・送信判定・出力採用・消費量・未確定状態を再計算します。**Pythonの最終判定をそのままLeanの入力にする構成ではありません。**

固定資料の比較、ハッシュ、定型文、累積点数の抽出は、観測を作る側の信頼境界です。Leanで証明するのはその観測値を受けるモデルの性質です。Python全体の全入力に対する意味的同値性や、暗号・JSON解析・OS・ファイルI/Oを形式証明したものではありません。

### CIが実行する検査

1. Pythonの239自己テストと、59記録・受信ファイル・採用文案の再検証。
2. 1,289ケースについて、PythonとHTML内JavaScriptの判定・状態遷移・記録JSONの一致。
3. Leanモデルのビルドと55定理の公理依存監査。
4. 1,289入力のモデル照合、8入力の判定集約6,561通り、59記録から派生させた295件の記録ビュー照合。

具体命題は、定義と証明を同じ小さいバッチにまとめて検査します。全体を一つの巨大なLeanファイルにしません。検査用ファイルは `.lake/` 配下で一時生成します。

`native_decide`、未完成の証明、独自公理で検査を迂回しません。公理依存は `propext`・`Quot.sound`・`Classical.choice` の許可集合と照合します。LeanやNode.jsがないときに、CI全体を成功扱いにする処理もありません。

```console
# Lean/ElanとNode.jsを導入した環境で
lake update
lake build
python poc.py ci
```

GitHubでは8ファイルを配置するだけで、push時に同じ検査を実行します。`lean.yml` の置き場所は必ず **`.github/workflows/lean.yml`** です。マニフェストはCI内で生成します。

## 公開範囲の設計

公開するのは、固定の小さなモデルで作用を確かめるための参照実装です。非公開システムを呼び出すだけの画面や、判定結果を表示するだけのモックにはしていません。一方、商用実装の内部設計をそのまま公開する構成にもしていません。

**公開する範囲：** 固定の合成データ、具体的な条件、決定的な項目変換、送信・出力採用の境界、単一対象の逐次台帳、記録の再計算、形式モデル、実装照合の手順。

**含めない範囲：** 汎用的な開示量推定や再識別評価、実文書の意味理解・個人情報検出・匿名化、差分プライバシーの機構、実際の法的根拠・権限・契約の判定、商用の分散台帳・同時実行制御、認証付き外部送信・時刻・結果照会、実運用の秘密・顧客ルール。

実施条件の相違を見せるため、公開ルールは意図的に単純化しています。この固定ルールが現実の住民情報を安全に扱うための十分条件である、とは主張しません。

## 第1弾との関係

第1弾は、回答案を業務に採用できる条件と根拠を確認する技術PoCです。第2弾は、その前後で情報の利用・送信・出力採用のプライバシー条件を確かめる技術PoCです。

本版の採用文案を次の回答採用検査へ渡す、という接続点は示せますが、**第1弾の既存JSONスキーマへの自動変換・実行時の一体化は本版には実装していません。** 第1弾のコードや条件は変更していません。両者を統合する段階では、共有する要求ID・証拠・用途・状態の対応を別途設計します。

## 編集時の注意

要求や台帳の型は厳格に確認します。壊れたJSON、重複キー、不正な型、未定義の設定は処理エラーで終了し、PASSやHOLDに読み替えません。

`policy` と `sources` はPython・JavaScript・Leanの共通参照ハッシュに固定しています。変更は、画面の文字を変えるだけの作業と区別してください。`cases.json` のテストを変更した場合もHTMLの `privacy-data` と同期し、期待値・証明照合の件数を再確認する必要があります。現配布物は同期済みです。

この版では数値を小さい非負整数に限定し、ASCIIのJSONキーを使用します。JSON正規化規格一般の完全実装ではありません。
